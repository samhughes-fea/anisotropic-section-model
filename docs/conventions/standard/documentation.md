# Documentation

Each repository has **one documentation home**: its Sphinx site on GitHub Pages,
built from the Markdown under `docs/` and the docstrings. There is no wiki and no
second copy of the manual. Markdown elsewhere in the repository is a signpost: a
few lines and a link to the manual page.

## The four manuals

The site is four manuals, after Code_Aster's U/R/V/D structure.

| Manual | Holds | Does not hold |
|---|---|---|
| **U**, use | Install, tutorials, how-to guides, API reference, defaults, errors, limits | Derivations (cite R) |
| **R**, reference | Definitions, assumptions and equation-by-equation derivations of every formula the code evaluates; the implementing function; limits | Usage recipes, evidence |
| **V**, validation | The code against closed forms, independent computations or published data, with the tolerance and the test that keeps it in CI | New theory |
| **D**, development | Architecture, workflow, testing, CI, releases, decisions, roadmap, bug log, feature log, tracker | User instructions |

Each manual has an index page (`docs/u/index.md`, `docs/r/index.md`, ...) with a
table of its documents keyed U0, R1, V1, D1. A page is cited by key, [R1], and an
equation by number, (R1.4). D links to this standard for anything shared rather
than restating it.

A small repository may start with U and D only, adding R and V when it has
theory to derive and results to validate.

## R documents

Every R document has eight parts, in order: problem; definitions and assumptions;
derivation; algorithm; implementation; limits; verification; references.

In the derivation:

- Start from a stated definition or a cited result, never from the final formula.
- One step per numbered equation; the sentence between two equations names the
  operation (substitute (R1.3), expand, use the definition of the centroid).
- Mark every approximation where it enters, with its order and validity range.
- End each result with the function that implements it and a check against a
  limiting case; list the check in the V manual.
- Name every symbol at first use and add it to the notation page, R0.

## Writing

- Complete sentences, British academic register (aerofoil, centreline, labelled),
  units stated, symbols defined at first use. No marketing words.
- **Transparency.** The manual answers what any reader might ask: install extras,
  defaults, errors, limits, performance, how to cite, stability, internals,
  testing, roadmap, defect history, governance.
- Internal pages (maintainer notes, plans, reports) start with a one-line
  **Audience: internal** banner.

## Equations

Inline maths is `$…$`. A numbered display is an `equation*` block with a `\tag`
carrying the document key (Sphinx wraps `$$…$$` that contains `\\` in `split`,
where `\tag` is not allowed). Follow each display with a sentence naming every
symbol not yet defined.

```tex
\begin{equation*}
\mathbf{x}_B = \mathbf{Q}(\theta)\,\mathbf{x}_S
\tag{R1.4}
\end{equation*}
```

## Citations

Cite with `{cite:t}` or `{cite:p}` against `docs/references.bib`
(sphinxcontrib-bibtex); the bibliography is printed once, in R0. Every `.bib`
entry is cited somewhere.

## Figures

- A manual figure is a MyST `{figure}` whose caption starts **Figure R1.1.**, says
  what is shown and names the example script that draws it.
- **Example figures are committed** (PNG) and embedded in the example's README.
  Commit a regenerated PNG only when the example's subject changed, because font
  rendering differs between machines.
- Never commit generated meshes or large exports (STL, OBJ, VTK); a script makes
  them.
- Diagrams are mermaid in the Markdown, one diagram per idea.

## Docstrings and the API reference

- NumPy style. Every public name has a docstring with Parameters, Returns, Raises
  and units.
- The API reference is generated by `sphinx.ext.autodoc`; prose pages link to it
  and never copy a docstring.
- `interrogate` reports public docstring coverage in CI.

## Build checks

`sphinx-build -W` (warnings are errors), `nitpicky` for cross-references, a link
check, and doctests where pages show code. `docs.yml` deploys `main` to Pages.

## Bug and feature logs

The D manual holds the curated records; GitHub Issues stays the live tracker.

| Record | Where | ID |
|---|---|---|
| Bug log | D manual, one table per area | `<AREA>-nnn`, e.g. `SG-004` |
| Feature log | D manual | `FD-nnn` |
| Tracker | D manual, generated from Issues at docs build | issue number |

A bug log entry is written **when the defect is found**, not after the patch:

| When | Required fields |
|---|---|
| Found | Next ID; index row **Open**; **Symptom**; **Evidence** (figure, input, test, metric); issue |
| Fix in hand | **Root cause**; **Fix** (behaviour and files); tests or figures named |
| Resolved | Status **Fixed**; **Verification** (the test or figure that proves it); PR; release |

Closed entries are never deleted; a wrong first diagnosis is struck through or
narrated. A follow-on of the same mechanism updates the same ID; a distinct
symptom gets a new one. An intended design change is not a bug.

## Repository files

| File | Role |
|---|---|
| `README.md` | What the package is, install, a minimal example, a figure, links to the manual |
| `CHANGELOG.md` | [versioning](versioning.md#changelog) |
| `CITATION.cff` | How to cite; version and date updated at each release |
| `SECURITY.md`, `CODE_OF_CONDUCT.md` | Synced community files |
| `docs/README.md` | Map of the docs tree |
| `src/**/README.md` | Ten to thirty lines: purpose, key imports, links |
